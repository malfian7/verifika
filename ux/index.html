Information Architecture

Empat grup, dua pintu masuk

Pengguna masuk lewat lapisan autentikasi, lalu bekerja di dua grup sidebar: Ruang kerja untuk pekerjaan harian dan Pengaturan untuk kebijakan serta integrasi. Akun dan notifikasi selalu tersedia di top bar.

Model navigasi

≥ 1040 px

Sidebar vertikal

Dua grup berlabel (Ruang kerja, Pengaturan) dengan penghitung item. Kuota halaman bulanan dan tombol Keluar di bagian bawah.

semua ukuran

Top bar kontekstual

Judul halaman aktif plus eyebrow konteks (mis. “Pengaturan”, ID sesi pindai). Lonceng notifikasi dan menu akun di kanan.

< 1040 px · < 560 px

Rail horizontal

Sidebar berubah jadi baris gulir horizontal; di ponsel hanya ikon. Label grup dan kuota disembunyikan.

User Flow

Lima alur yang menentukan pengalaman

Alur inti adalah validasi satu dokumen: semua alur lain melayaninya — masuk ke sistem, memproses dalam jumlah besar, mengatur kebijakannya, atau mengalirkan hasilnya ke sistem lain.

Mulai Aksi pengguna Proses sistem / AI Keputusan Selesai berhasil Selesai ditolak / ditahan Kembali / ulangi

Validasi satu dokumen

Aktor
Rina (analis verifikasi)
Pemicu
Pengajuan baru masuk dari cabang atau nasabah
Tujuan
Data dokumen terverifikasi masuk ke core system tanpa diketik ulang
Titik rawan (hipotesis)
  • Foto buram atau terpotong memaksa putaran unggah ulang
  • Field alamat & RT/RW paling sering salah baca
  • Alasan dokumen ditahan harus bisa dijelaskan ke nasabah
Metrik keberhasilan
  • Waktu per dokumen < 90 detik
  • ≥ 85% dokumen lolos tanpa koreksi field
  • Fraud lolos ke core system = 0

Login dan lupa password

Aktor
Semua persona
Pemicu
Awal hari kerja atau sesi habis
Tujuan
Masuk ke ruang kerja dengan aman dan cepat
Titik rawan (hipotesis)
  • Captcha sulit dibaca — sediakan tombol muat ulang
  • Email OTP masuk folder spam
  • Salah password berulang tanpa petunjuk
Metrik keberhasilan
  • ≥ 95% login berhasil pada percobaan pertama
  • Pemulihan akun < 3 menit tanpa tiket IT

Proses batch berkas

Aktor
Rina (analis verifikasi)
Pemicu
Kiriman berkas sekaligus dari cabang
Tujuan
Memproses puluhan berkas dan hanya menyentuh yang bermasalah
Titik rawan (hipotesis)
  • Jenis dokumen salah dikenali otomatis
  • Menunggu tanpa kabar — perlu progres per berkas
  • Sulit menemukan berkas gagal di antrean panjang
Metrik keberhasilan
  • 40 berkas selesai < 2 menit
  • ≤ 10% berkas butuh tinjau manual

Mengubah ambang & aturan

Aktor
Hendra (kepala risiko & kepatuhan)
Pemicu
Tren fraud baru atau antrean tinjau terlalu panjang
Tujuan
Menyesuaikan kebijakan tanpa tiket IT dan tahu dampaknya
Titik rawan (hipotesis)
  • Takut mengubah ambang tanpa bukti dampak
  • Aturan saling bertabrakan — aksi terberat yang menang perlu dijelaskan
  • Perubahan harus bisa dipertanggungjawabkan ke auditor
Metrik keberhasilan
  • Perubahan kebijakan < 1 hari (sebelumnya berminggu-minggu)
  • Beban tinjau manual tetap < 5%

Integrasi API & webhook

Aktor
Dimas (engineer integrasi)
Pemicu
Proyek menghubungkan LOS / core banking ke Verifika
Tujuan
Permintaan pertama berhasil dan event mengalir ke sistem internal
Titik rawan (hipotesis)
  • Key bocor jika ditampilkan berulang — tampil sekali + rotasi
  • Webhook gagal diam-diam — perlu log & retry
  • Pesan error generik menyulitkan debugging
Metrik keberhasilan
  • Waktu ke respons 2xx pertama < 30 menit
  • Tingkat sukses webhook ≥ 99%

Proto Persona

Tiga orang yang memakai Verifika

Satu persona primer yang bekerja di dalam aplikasi sepanjang hari, satu pemilik kebijakan, dan satu engineer yang menghubungkannya ke sistem lain. Nama dan detail bersifat fiktif.

RWRina WulandariAnalis Verifikasi DokumenPrimer

“Saya tidak keberatan sistem yang membaca, asal saya tahu bagian mana yang harus saya cek ulang.”

Usia29 tahun
LokasiKantor pusat, Jakarta
Pengalaman4 tahun operasional kredit
PerangkatLaptop + 2 monitor, ponsel

Tujuan

  • Menuntaskan ±120 dokumen sebelum cut-off 16.00
  • Minim salah input yang dikembalikan supervisor
  • Cepat mengenali dokumen mencurigakan

Frustrasi

  • Mengetik ulang data KTP & STNK ke core system
  • Foto buram dari cabang → minta ulang lewat chat
  • Tidak tahu alasan dokumen ditolak sistem lama
  • Membuka 3 aplikasi untuk satu pengajuan

Perilaku

  • Memproses batch pagi hari, tinjau manual siang
  • Teliti di field nama dan alamat
  • Suka pintasan keyboard
